# 业码汇

<p align="center"><img src="docs/assets/yemahui-banner-large.png" alt="业码汇" width="100%"></p>

业码汇（FirmMatterCodeManagement）是面向会计师事务所、税务师事务所及其他专业服务机构的业务编号与项目管理系统。

项目覆盖项目分配、业务编号、签字人、开票登记、收款登记、权限管理和 Excel 导出。

## 功能概览

- 管理人员、执业人员、后勤行政三类角色及权限控制
- 按编号年度、事务所、业务类型维护自定义编号规则
- 项目负责人和团队成员分配，支持姓名、拼音搜索
- 报告编号生成、回收和历史追踪；旧编号不会因重新发号而丢失或复用
- 项目首次发号后锁定事务所、业务类型和业务年度，保持已发编号的归属信息一致
- 项目列表默认按当前编号年度筛选；按审计对象所属年度查询时使用 `report_year` 参数
- 发票和到账逐笔登记，自动汇总项目开票、收款及余额
- 签字人绑定执业人员账号，支持重名、启用、禁用、导入和导出
- 执业人员在“我签字的项目”中查看当前登录编号年度内本人签字的项目；查询其他编号年度需先切换网页登录的编号年度
- 看板统计包含本人签字项目；项目导出保留签字账号用于区分同名人员
- 项目和签字人 Excel 导出
- 首次启用向导：自定义管理员、事务所、业务类型和编号模板

## 技术栈

- 前端：React 18、TypeScript、Vite、Tailwind CSS、Radix UI
- 后端：Python、FastAPI、SQLAlchemy、SQLite、openpyxl
- 认证：JWT

## 环境要求

- Python 3.11 或更高版本
- Node.js 18 或更高版本（仅开发和重新构建前端时需要）

## 快速启动

### Windows 服务器一键部署

从 [GitHub Release](https://github.com/byttao/FirmMatterCodeManagement/releases) 下载 `FirmMatterCodeManagement-win-x64.zip`，解压到固定目录，双击 `Manager.exe` 并授予管理员权限。设置监听范围、端口及可选的外部 IP 或域名后，点击“一键启动”。管理工具会安装开机自启的 Windows 服务、配置入站防火墙，并打开本机首次启用页面。完整步骤见 ZIP 内的 `安装与初始化.html`。

安装包中的两个 EXE 已包含 Python 运行时；正式使用无需安装 Python 或 Node.js，发布 ZIP 不再附带额外的 Python 安装包。域名需自行配置 DNS；公网访问业务数据时需另行配置 HTTPS 反向代理。

Windows 版在管理工具中检查 GitHub 新版本，可自动下载并升级；也可先下载最新 ZIP，再在管理工具中选择该文件离线升级。升级会停止服务、备份 SQLite 数据库、替换程序并验证新服务，失败时尝试恢复原程序和数据库。业务数据、密钥及服务器配置保存在解压目录的 `data` 中，迁移服务器时须一并保留。未创建数据库的首次安装目录可直接升级，无需备份空库。

### 开发模式

```bash
cd backend
python -m pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

另开终端启动前端：

```bash
cd frontend
npm install
npm run dev
```

浏览器访问 `http://localhost:5174`。

### 单体模式

先执行 `npm run build`，将 `frontend/dist` 内容复制到 `backend/static`，再运行：

```bash
cd backend
python main.py
```

浏览器访问 `http://localhost:8000`。仓库只包含通用源码，旧版 Windows 启动脚本留在原工作目录，不作为新安装入口。

## 首次启用

首次打开系统会自动进入安装向导。请按向导完成：

1. 创建管理员账号和至少 8 位密码。
2. 选择首个编号年度。
3. 填写事务所名称。
4. 为每个事务所添加业务类型和编号模板。

编号模板支持以下占位符：`{yyyy}` 为四位编号年度（2026），`{yy}` 为两位编号年度（26），`{n}` 到 `{nnnnnnnnnn}` 为序号并按 n 的数量补零（例如 `{nnn}` 生成 `001`）。模板必须包含 `{yyyy}` 并且只能包含一个序号占位符，可以加入事务所自定义的固定前缀、后缀或中文文字。当前不使用月份、日期等随生成时间变化的占位符，以保证编号年度内格式稳定。安装完成后，使用新建账号登录，再到“用户管理”“签字人管理”和“编号年度配置”继续维护。
请先创建执业人员账号，再在签字人管理中按账号关联所属事务所。同名人员由登录账号区分；Excel 导入也使用账号，不按姓名猜测。
同一年度的独立编号规则必须使用不同的完整格式；多个业务类型需要共用同一序列时，可以在编号年度配置中关联同一规则。

编号年度是项目建立和发号所属的年度，业务年度是审计对象所属的年度。两者分别保存。例如 2026 年为同一客户办理 2024 年度和 2025 年度审计，应建立两份项目；若使用 `{yyyy}-{nnn}` 模板，两份报告编号依次为 `2026-001`、`2026-002`。

系统不会自动创建默认账号、示例事务所或示例文号。运行数据保存在 `backend/data/db.sqlite`，已通过 Git 忽略，不应提交到代码仓库。

出于首次安装安全考虑，安装向导需要在运行后端的电脑上打开；安装接口只接受本机请求。默认服务也只监听 `127.0.0.1`。需要局域网访问时，完成安装后再通过 `FIRM_MANAGER_HOST` 和 `FIRM_MANAGER_PORT` 配置监听地址与端口。

## 数据与配置

默认数据库路径为 `backend/data/db.sqlite`。部署时可以通过 `FIRM_MANAGER_DATA_DIR` 指定数据目录，或通过 `FIRM_MANAGER_DATABASE_URL` 指定 SQLite 文件连接串。当前自动迁移仅支持 SQLite。

### 已部署系统升级

升级分为程序文件和数据库两部分。数据库迁移是自动的；程序文件可用仓库根目录的 `upgrade.py` 一条命令完成下载、版本校验、数据库备份和替换。脚本会随版本自更新，不覆盖业务数据、JWT 密钥、环境变量或已构建的静态目录。若文件替换中途失败，脚本会尝试恢复本次修改过的程序文件；数据库备份仍会保留。

```bash
python upgrade.py                 # 只检查 GitHub 最新 Release
python upgrade.py --apply         # 停止后端后备份数据库并更新程序文件
python upgrade.py --target 0.1.10 --apply
```

脚本需要能访问 GitHub，且应在后端停止后运行。指定旧版本也会被拒绝，以免旧程序误读新数据库。更新完成后启动后端，数据库会按 `schema_migrations` 自动迁移；迁移失败会回滚并阻止服务启动。脚本不会猜测 Windows 服务、Docker 或其他进程管理器的重启命令，部署到这些环境时需由现有进程管理器负责停止和重启。

**从 v0.1.8 或 v0.1.9 升级的注意事项：**这两个版本的旧升级脚本会保留自身。首次升级到 v0.1.10 后，请从 v0.1.10 Release 源码包中取出根目录的 `upgrade.py`，替换安装目录中的同名文件一次；之后升级器才会随版本自动更新。使用 `git pull` 更新源码的安装方式不受此限制。

使用前后端分开部署时，升级后刷新前端即可。使用单体模式时，`backend/static` 为部署机上的构建目录，不会被源码升级覆盖；请在有 Node.js 的环境运行 `cd frontend && npm ci && npm run build`，再把 `frontend/dist` 内容复制到 `backend/static`。

1. 停止正在运行的后端，并保留整个数据目录（数据库及 `jwt_secret`）。不要把数据目录覆盖为新版本中的文件。自定义数据目录或数据库连接串应使用绝对路径；升级脚本找不到数据库时会停止，以免误把空库当成旧数据。
2. 运行 `python upgrade.py --apply`，或获取新版本源码/发布包后安装依赖；若使用单体模式，重新构建前端并部署到 `backend/static`。
3. 启动新版本后端。启动时按 `schema_migrations` 中的版本记录自动执行尚未运行的数据库迁移；旧库首次升级时会在数据库旁自动生成 `*-before-upgrade-时间.sqlite` 备份，后续无迁移的启动不会重复备份或重复导入数据。
4. 确认启动成功、能够登录，并抽查项目数量、编号历史及财务流水。自动备份包含业务数据，应与数据库一样妥善保管。

迁移在 SQLite 事务内执行，任何步骤失败都会回滚并阻止后端启动；错误信息会给出备份路径。恢复时先停止后端，保留失败后的数据库及可能存在的 `-wal`、`-shm` 文件，再把备份复制回原数据库路径，使用原版本程序启动排查。数据库版本高于程序支持的版本时，旧程序也会拒绝启动，避免误写新数据。

数据库结构可以随新版本自动升级；程序文件目前可由升级脚本自动下载和替换。进程停启、Python 依赖更新及单体模式的前端构建仍须接入具体部署流程。脚本的文件回退只处理正常抛出的写入错误；断电或强制终止时应从数据库备份和原版本发布包恢复。

从旧版本升级时，首次启动会把项目原有开票、收款汇总各迁移为一条标记为“旧版汇总数据”的记录；原数据没有登记日期时会显示“日期未登记”。迁移按项目记录已完成状态，不会在后续启动时重复导入。
旧版签字人会保留姓名及项目签字历史，但默认处于“待关联”状态。管理员需在签字人管理中逐条确认执业人员账号；关联前不能选作新项目的签字人。已有项目仍可查看和编辑其他字段。
编号历史升级时会补录数据库中当前保存的报告编号，此后每次发放与回收都会留存记录。旧版本中已经被新编号覆盖的更早编号无法从当前数据库可靠恢复。已发放编号的规则模板不能更改，新规则也不能复用与历史编号冲突的格式。旧版年度、签字人和用户列表 API 已合并到当前接口；外部客户端升级时也需同步更新调用。

JWT 签名密钥首次启动时自动生成在数据目录的 `jwt_secret` 文件中。也可通过 `FIRM_MANAGER_SECRET_KEY` 设置至少 32 个字符的密钥。前后端分开部署时，可用 `FIRM_MANAGER_CORS_ORIGINS` 指定允许的前端来源，多个来源用英文逗号分隔。

## 角色说明

- 管理人员：全部功能
- 执业人员：查看自己负责、参与或签字的项目；仅可编辑自己负责的项目
- 后勤行政：查看项目，维护财务信息，导出数据，管理签字人；不能删除项目或回收编号

## 版本发布

每次推送都应对应一个递增版本号和 GitHub Release。提交说明与 Release 标题、更新说明使用简短中文，概括版本号及主要修改。正式发布前执行后端集成测试与前端构建，并确认运行数据库、密钥、工作记忆和构建产物未进入 Git 暂存区。
